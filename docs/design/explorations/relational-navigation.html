Featherbase · Design exploration

Navigating a relational world

Six interactive patterns for moving between related rows — every demo below is clickable and runs on the same hypothetical dataset. The fake URL bar in each demo shows the real Featherbase route the click would produce (the list route already accepts ?filters=… today).

Purchase Order→its Lines (child rows)
Employee→their Attendance & Payroll (backlinks)
Payroll Slip→its Employee (a reference, hopped forward)

Who has tried this

Every serious low-code tool has converged on some subset of the same six ideas. None ships all of them — which is the opportunity.

Frappe / ERPNext → Pattern 1

A "Connections" section on every form: backlinked doctypes grouped with counts, declared per-doctype in a dashboard file. Click → filtered list.

Odoo → Pattern 2

"Smart buttons" — count badges at the top of a form that jump to a filtered list, with a breadcrumb trail that always leads back.

Salesforce / Airtable Interfaces → Pattern 2

Related lists embedded as tabs or sections inside the record page itself; drill-down hierarchies (Project → Task → Subtask).

Airtable / NocoDB → Pattern 3

Linked-record cells expand into a side panel without leaving the grid; NocoDB shows the link count in the cell and opens a child list.

Tableau / Looker → Pattern 4

Cross-filtering: click a mark in one pane and every other pane filters to match. Selection is the filter.

MS Access → Pattern 5

Subdatasheets — the 1999 idea that still works: a chevron on each grid row expands its child rows inline.

macOS Finder → Pattern 4

Miller columns: cascading panes where each selection populates the pane to its right. The same geometry as cross-filtering.

Glide → Patterns 2 & 3

Relation collections on a details screen; tapping an item pushes its own details screen, nested indefinitely — navigation as a stack.

The playground

Dataset: Suppliers → Purchase Orders → PO Lines → Items (procurement) and Employees ← Attendance / Payroll / Leave (HR), with a self-reference (reports to) thrown in to keep the patterns honest.

1 · Connections panel

Borrowed from Frappe — but derived automatically from metadata instead of hand-declared

Every form gets a panel listing every table that points here, with live counts. Featherbase can derive this with zero configuration: the reverse-lookup query ("which Reference columns target this table?") already exists in the server for delete-blocking. Child tables stay inline in the form; the panel covers true backlinks — including via sub-tables (Item ← PO Line ← Purchase Order, Frappe's "internal links").

Try: click Payroll Slip in the panel → filtered list with a removable chip → breadcrumb back. Switch the root record to see the panel recompute per table. Note the greyed zero-count rows and the "+" (create pre-filled).

2 · Smart counters + related tabs

Borrowed from Odoo's smart buttons and Salesforce's related lists

The related rows live inside the record page: count tiles up top double as tab switches, and each tab embeds a real (read-only) list of the related table with an escape hatch to the full filtered list and a pre-filled "+ New". Highest information density of any pattern — and the strongest claim that "the employee page is the employee 360°".

Try: click the count tiles, open a payroll row from inside a tab (breadcrumb grows), then switch employee — tabs and counts recompute from metadata.

3 · Peek panels (a navigation stack)

Borrowed from Airtable's expanded records and Glide's pushed detail screens

Clicking a reference doesn't navigate away — it slides a panel over the current screen. Panels stack: peek at the employee from a payroll slip, then peek at her attendance from there, and the trail stays visible as layered edges. You never lose the list you started from. Each panel offers "open full ↗" when a glance isn't enough.

Try: click any payroll row → in the panel click Priya Raman → then Attendance → then a row. Four panels deep, one Esc (or ✕) back to where you were. The back arrow pops one level.

4 · Cross-filter workspace

Borrowed from Tableau's filter actions, with Miller-column geometry from the Finder

Three live panes — Suppliers, their Purchase Orders, and the Lines inside those. Clicking a row in any pane is the filter: everything downstream narrows instantly, aggregates included. Selections accumulate (click two suppliers to compare). This is less "navigate to a record" and more "interrogate the relationship" — a different job than Patterns 1–3, and the strongest candidate for a separate Explore surface next to Dashboards.

Try: click Acme Metals, then also Zenith Polymers; then narrow to one PO. Watch the counts, the ₹ totals, and the chips — click a chip's ✕ to release that filter.

5 · Expandable rows in the list

Borrowed from MS Access subdatasheets and AG Grid master-detail

The child rows come to you: a chevron on each Purchase Order expands its Lines inline, several at once if you like, without ever leaving the list. Perfect for the "scan ten POs and eyeball their lines" job that Patterns 1–3 make tedious. Costs one indent level per hop, so it's best kept to one level deep.

Try: expand two or three POs at once and compare their lines side by side. Each expansion shows its own line count and total; the supplier stays clickable.

6 · Relationship map

Nobody ships this well — the speculative one

The current row sits in the middle; what it points at fans left, what points at it fans right (dashed = a collection with a count). Click any collection to open its rows below; click any record node to re-center the whole map on it. Because Featherbase is metadata-driven, this view is free for every table — it's the schema made walkable. Probably not the daily driver, but a superb "where am I?" view and a great schema-comprehension tool for builders.

Try: from Priya Raman, click the Payroll Slip collection, pick a slip → the map re-centers on the slip, whose own neighborhood now shows Employee on the left. Follow reports to to walk up the org chart. The trail below the map takes you back.

How I'd layer them in Featherbase

These aren't competing options — they're layers with different jobs. The order below is sorted by leverage: what the codebase already makes cheap, first.

Ship now

Make references clickable + auto Connections panel (Pattern 1)

Today a Reference field renders as a plain autocomplete with no way to visit the referenced row — that's the single biggest gap. Add link-out on every Reference control, and a Connections card on FormView. Both endpoints already exist: the reverse-lookup SQL sits in document.ts (delete-blocking), and ListView already accepts ?filters=[["employee","=","EMP-001"]]. Counts come from the existing /api/dashboard/count. Zero new metadata.

Next

Peek panel (Pattern 3)

One generic slide-over that renders read-only FormView for any (table, id) — instantly upgrades every reference link and every Connections row from "navigate away" to "glance first, commit later". Stack depth comes free from an array in state.

Next

Related tabs (Pattern 2), opt-in per table

A small piece of Table metadata ("show Attendance and Payroll as tabs on Employee") turns hub records into 360° pages — this is Frappe's dashboard-links idea, but declared in table_def instead of Python files. The embedded lists are just ListView with a fixed filter.

Later

Cross-filter Explore surface (Pattern 4) · Expandable rows (Pattern 5)

Explore is a new surface (pairs beautifully with the existing Dashboards), not a form feature — worth doing when analysis becomes a real user job. Expandable rows are a ListView option for tables with children; watch interaction with virtualization.

Garnish

Relationship map (Pattern 6)

Cheap to derive from the same metadata, memorable in demos, genuinely useful on the All Tables / builder side as a schema browser. Not a daily navigation tool.
