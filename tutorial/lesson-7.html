Letting the tests see the code

We want to know which lines no test proves. The tool for that is called coverage, and the first time we switch it on it shows us nothing at all. This lesson finds out why and fixes it, without leaving any code unproven on the way.

What makes a change a refactor?

The tests pass before and after, and the tests' expectations are not changed.

How do our tests start Featherbase at this point?

They run bun start as a separate program on port 3210 and wait until it answers.

Question 1What is coverage?

While the tests run, the test tool notes which lines of your code actually ran. A line that never ran is a line that no test proves. Coverage is the report of that.

Question 2What happened when we switched it on?

Predict before you look

Our two tests pass, and between them they exercise every line of the program. We run bun test --coverage. What percentage do you expect?

Show the result
 2 pass
 0 fail

No percentage. No table at all. The report was empty.

The reason: the tests start Featherbase as a separate program. Bun measures only the program that runs the tests. It was watching the test file and nothing else.

Question 3What can we do about it?

A. Keep the separate program and measure that

It would keep the tests exactly as they are.

Problem: Bun measures coverage only inside bun test. A dead end.

B. Start Featherbase inside the test's own program We chose this

Split the file in two: one builds the app, a tiny one starts it. The test takes the built app and starts it itself.

Costs: the test now takes one thing from our code. And these tests would no longer run bun start, so its proof has to move somewhere else: Question 5.

C. Adopt a testing library that does B for us

Less code in the tests.

Why not yet: it hides what is going on. Better to do it once by hand and know what such a library saves.

D. Do not measure lines; only check every criterion has a test

Simple.

Bites later: it cannot find code that no criterion asked for, which is the main thing coverage catches.

Question 4What does the split look like?

featherbase.ts (builds the app)

import { html } from "@elysiajs/html";
import { Elysia } from "elysia";

const welcomePage = "<!doctype html><title>Featherbase</title><h1>Welcome to Featherbase</h1>";
const notFoundPage = "<!doctype html><title>Page not found</title><h1>Page not found</h1>";

export function createFeatherbase() {
  return new Elysia()
    .use(html())
    .get("/", () => welcomePage)
    .onError(({ code }) => {
      if (code === "NOT_FOUND") return notFoundPage;
    });
}

start.ts (only starts it)

import { createFeatherbase } from "./featherbase.ts";

createFeatherbase().listen(Number(process.env.PORT ?? 3000));

export means other files may use createFeatherbase. In the test file, two helpers change:

features/foundations/home/home.test.ts

function startFeatherbaseOnAFreePort() {
  featherbase = createFeatherbase().listen(0);
  address = `http://localhost:${featherbase.server?.port}`;
}

async function stopFeatherbase() {
  await featherbase.stop();
}

listen(0) means "pick any free port". The next line asks which one was picked.

Two things we wrote in lesson 1 disappear from the Home tests: the fixed port 3210, which would have clashed as soon as two test files ran, and the wait loop, because the app is ready the moment listen returns.

Why is the app ready the moment it returns, when before we had to wait?

It is about who is ready when. We asked a freshly started server for a page with no waiting at all:

same program:     asked right after listen()  → answered 200
separate program: asked right after spawn()   → no answer (refused)
separate program: first answer after 6 knocks, 59 ms

Two programs, as in lessons 1 to 6.

test ── spawn("bun start") ──► returns AT ONCE: "the program exists"
                                 meanwhile, in the other program:
                                 start Bun → read files → build app → open port
test ── "are you up?" ──► refused … refused … refused … 200   ← must knock

spawn hands control back the moment the other program exists, not when it is ready. The test cannot see inside it, so all it can do is knock until something answers.

One program, from this lesson on.

test ── createFeatherbase().listen(0) ──► builds the app, opens the port,
                                          and only THEN returns
test ── next line: open the page ──► answered 200   ← nothing to wait for

listen does not return until the port is open, because the work happens on the test's own line of code. By the time the next line runs, the server is already listening. The wait loop only ever covered the gap between "started" and "ready", and that gap is gone.

Think of a shop. Spawning is phoning a shop and ringing until someone picks up. Listening is opening the shop yourself: you are inside when the door opens.

A step further

"Started" and "ready" being different moments is behind most flaky tests. Every fixed sleep(500) in a test suite is a guess at that gap. Removing the gap beats guessing it.

Question 5Where does the proof of bun start go?

Until now, the Home tests ran the real bun start, so every run also proved that the front door works. If they stop doing that and nothing takes over, start.ts is proven by nothing. We tried it: with the spawn code simply deleted and a typo put into start.ts, every test passed while Featherbase could not start:

bun test     2 pass, 0 fail
bun start    ReferenceError: createFeatherbas is not defined

So the spawn-and-wait code is not deleted. It moves, word for word, into a test of its own, with its own criterion in a folder named for the action:

features/foundations/starting/starting.md

# Starting

The scene: someone runs Featherbase.

## Acceptance criteria

1. Running `bun start` opens Featherbase on the port it is given.

features/foundations/starting/starting.test.ts

test("Running `bun start` opens Featherbase on the port it is given.", async () => {
  const page = await fetch(address).then((response) => response.text());
  expect(page).toContain("Welcome to Featherbase");
});

Its beforeAll uses lesson 1's three helpers, startFeatherbase, waitUntilFeatherbaseAnswers and featherbaseAnswers, moved unchanged: run bun start on port 3210 and knock until it answers. "The port it is given" is how a hosting service tells a program where to listen. Now the same typo is caught at once:

error: Featherbase did not start at http://localhost:3210
 2 pass
 1 fail
The rule

A refactor must not remove the only proof of something. Move the proof; do not delete it.

So the wait loop is back?

Only here, where a separate program really does take a moment to start. The Home tests, which now run Featherbase in their own program, no longer need it.

Question 6Can coverage see the code now?

All files       |  100.00 |  100.00

Yes. Every line of featherbase.ts is run by the tests. The Home tests also got faster, from 431 to 353 milliseconds, because they no longer start a second program and wait for it.

The test file changed. Is this still a refactor?

Lesson 5 said a refactor leaves the tests untouched. Here the test file changed: how Featherbase is started and stopped. What each test promises did not. The diff of the test file changes no test( line and no expect( line:

git diff d7022ca 2c40cef -- features/foundations/home/home.test.ts \
  | grep -E '^[-+]\s*(test\(|expect\()'
# prints nothing

The bun start check is the same code in a new file, under a name of its own. So the honest wording is: the tests' expectations are untouched. When a refactor has to change the set-up around the tests, check that line by line, as above.

This is a refactor: commit.

Look closer

Look at that table once more. One of our files is missing from it. Which one, and what does its absence mean?

Show the answer

start.ts is missing. It is not at 100%. It is not measured at all, because it runs only inside the second program that bun start starts, and coverage measures only the program running the tests. A coverage report only lists files the tests touched. It is not unproven, though: the starting test proves it by what it does. Silence in a report is not the same as a pass, so know which proof covers what the report leaves out.

The habit to take away

When a report looks clean, ask what it is not showing you. An empty or shorter-than-expected report is a finding in itself.

A step further

This is the in-process versus out-of-process trade. In-process gives coverage, free ports and no readiness polling, at the cost of the test importing a composition root. Keep one out-of-process smoke test for the real entry point, which is exactly what the starting test is.

Try it yourself

git checkout d7022ca && bun install && bun test --coverage   # no table
git checkout 2c40cef && bun install && bun test --coverage   # the table appears

The first run prints no table. The second does.

Check yourselfAnswer, then open each one

What does coverage tell you?

Which lines of your code ran while the tests ran. Lines that never ran are proven by no test.

Why was the first coverage report empty?

Featherbase ran as a separate program, and Bun measures only the program running the tests.

What does listen(0) do?

It starts the app on any free port chosen by the computer.

Which two pieces of lesson 1's test disappeared from the Home tests, and why?

The fixed port, since the computer now picks a free one, and the wait loop, since the app is ready as soon as listen returns.

Why could the wait loop go?

listen returns only once the port is open, because it runs on the test's own line. A separate program, started with spawn, is not ready when spawn returns, so the test had to knock until it answered.

A typo in start.ts: do the tests catch it at this commit?

Yes. The starting test runs the real bun start, which fails, so the test fails.

Why is start.ts missing from the table, and is that good news?

It runs in a second program, which coverage cannot see. It is still proven: the starting test checks it by what it does.

What must a refactor never remove?

The only proof of something. Move the proof instead.
