The first failing test

We want a page that says "Welcome to Featherbase". In this lesson we write no page at all. We write the proof that the page is missing, and we save that failure on purpose.

Commit: red About 20 minutes
Stop and guess first

You are asked to build a web page that says "Welcome". What is the very first file you would create: the page, or something else?

Question 1What exactly are we trying to prove?

One thing, written as one plain sentence:

Opening Featherbase shows "Welcome to Featherbase".

This sentence is called an acceptance criterion. It means: the work is accepted when this is true. Not when the code looks clever, and not when the programmer says it is done.

Before any code, we write it into a small text file that a non-programmer can read:

features/foundations/home/home.md

# Home

The scene: a person opens Featherbase.

## Acceptance criteria

1. Opening Featherbase shows "Welcome to Featherbase".
Why a separate file? The test will say the same thing.

Because the two files have different readers. The .md file is for the person who decides what the product must do. They approve it before any code exists. The test is the proof, written for the computer.

The cost is one sentence typed twice. A later lesson adds a check that fails if the two ever differ.

Question 2What are the ways to test that a page shows some words?

There are at least four. They run from simple to thorough, and the simple ones each hide a trap.

1. Call the code that makes the page

The test calls a function and checks the text it gives back. Three lines.

Bites later: it tests the inside. It never proves the program starts, or that anyone can reach the page. Rearranging the code breaks the test even when nothing is wrong.

2. Ask the app directly, with no browser

The test hands the app a request and reads the page it returns. Very fast.

Bites later: it cannot see what only a browser shows, such as a button that works by script.

3. Start the real program and fetch the page

Proves the program starts and answers.

Bites later: still blind to what a browser does with the page.

4. Start the real program and open it in a real browser We chose this

Proves the whole chain, the way you would check it by hand.

Costs: the slowest, about a second, and the most setup code.

Why the slowest one?

Because this is the first test of the project. Its job is to prove, once, that everything is connected: the program starts, a browser reaches it, and the words appear. Later tests can use faster ways, because this one already guards the chain.

A step further

This is the "walking skeleton" idea: the first test goes end to end through the thinnest possible slice, so the tooling is forced into existence by a real need. Most later criteria should drop to way 2. Keep way 4 for a handful of journeys.

Question 3What does the test look like?

Read only the top of the file first. It is written to read like a table of contents.

features/foundations/home/home.test.ts

beforeAll(async () => {
  startFeatherbase();
  await waitUntilFeatherbaseAnswers();
  await openBrowser();
});

afterAll(async () => {
  await closeBrowser();
  stopFeatherbase();
});

test('Opening Featherbase shows "Welcome to Featherbase".', async () => {
  const page = await openFeatherbaseInNewTab();
  expect(await textOn(page)).toContain("Welcome to Featherbase");
});

Three blocks, and you can read each one aloud:

  • Before the tests: start Featherbase, wait until it answers, open the browser.
  • After the tests: close the browser, stop Featherbase.
  • The test: open Featherbase in a new tab and expect the welcome words.

Notice the test's name. It is the acceptance criterion, word for word.

Question 4Who is talking to whom?

This short test runs four separate programs at once. Once you can see who is who, every line makes sense.

 bun test            (1) the test runner: finds *.test.ts files and runs them
   │
   ├─ Bun.spawn ──►  (2) Featherbase: bun start, listening at localhost:3210
   │                        ▲                  ▲
   ├─ fetch ── "are you up?"┘                  │
   │                                           │
   └─ Playwright ──► (4) a real Chromium, with no window, opening the page
      (3) a library inside the test that drives the browser
  • (1) bun test gives us test, expect, beforeAll and afterAll.
  • (2) Featherbase is started the way a person would start it. The test never looks at its code. The only thing the two share is an address. That is what lets us change everything inside later without touching this test.
  • (3) Playwright is the one package we install. It sends a browser instructions: open a tab, go to this address, read the text.
  • (4) Chromium is the browser it drives. It is "headless": it draws pages exactly as Chrome does, but shows no window.

The order of events:

beforeAll  start Featherbase ─► wait until it answers ─► open the browser
test       open a new tab at the address ─► read its text ─► expect the words
afterAll   close the browser ─► stop Featherbase

beforeAll and afterAll run once for the whole file, not once per test. Starting a program and a browser is slow, so later files with many tests share one of each.

Question 5How does each step work?

Here is the rest of the file, the helpers below the three blocks.

function startFeatherbase() {
  featherbase = Bun.spawn(["bun", "start"], { env: { ...process.env, PORT: "3210" } });
}

async function waitUntilFeatherbaseAnswers() {
  const giveUpAt = Date.now() + 3000;
  while (!(await featherbaseAnswers())) {
    if (Date.now() > giveUpAt) throw new Error(`Featherbase did not start at ${address}`);
    await Bun.sleep(100);
  }
}

function featherbaseAnswers() {
  return fetch(address).then(
    () => true,
    () => false,
  );
}

async function openBrowser() {
  browser = await chromium.launch();
}

async function openFeatherbaseInNewTab() {
  const page = await browser.newPage();
  await page.goto(address);
  return page;
}

function textOn(page: Page) {
  return page.innerText("body");
}

async function closeBrowser() {
  await browser?.close();
}

function stopFeatherbase() {
  featherbase.kill();
}

Starting. Bun.spawn(["bun", "start"]) runs bun start as a separate program, exactly as you would type it in a terminal. env: { ...process.env, PORT: "3210" } copies every setting the test already has and adds one more, the port. So the test knows where to knock.

Waiting. Bun.spawn returns the moment the program exists, not when it is ready. A server needs a moment before it listens. If the test went straight on, it would sometimes knock too early and fail at random. So waitUntilFeatherbaseAnswers knocks every 100 milliseconds (Bun.sleep(100)), and after 3 seconds it gives up with a message that says what went wrong.

Knocking. featherbaseAnswers asks one yes-or-no question:

fetch(address)        send a request to the address
  .then(              when it finishes, run ONE of these two:
    () => true,       it got a reply        → true
    () => false,      nobody was listening  → false
  )
  • fetch does not hand back the reply at once. It hands back a promise, an IOU for a result that arrives later. A promise ends in one of two ways: it succeeds or it fails.
  • .then(first, second) runs first on success and second on failure. () => true is a tiny function with no inputs that gives back true.
  • Without the second function, "nobody listening" would be an error and would stop the loop at the first knock. With it, "not started yet" is an ordinary false, and the loop knocks again.
  • Any reply counts as true, even "404 Not Found": the server answered. Whether the page is right is the test's job, not this function's.

Think of a doorbell. If someone answers, whatever they say, the answer is yes. If nobody comes, you ring again in a moment. You don't call the police.

await means "wait here for that IOU to be paid". It appears on almost every line because each line asks another program something and needs its answer before going on.

Reading. page.innerText("body") reads the text a person would see, not the HTML underneath. If the welcome words were hidden by styling, the test would fail, and it should. toContain asks "are the words on the page somewhere?" rather than "is the page exactly this?", so adding a sidebar later will not break this test.

Cleaning up. browser?.close(): the ?. means "only if there is a browser". If starting failed, beforeAll stopped before the browser opened, and cleanup must not crash on top of that.

The habit to take away

There is not one comment in that file. Each small function has a name that says what it does, even when its body is a single line. If you feel the need to write a comment, try naming a function instead.

Question 6What do we install?

Only what the test needs in order to run. The test imports one outside tool, Playwright, which drives a real browser. So one package goes in:

package.json

{
  "name": "featherbase",
  "private": true,
  "type": "module",
  "devDependencies": {
    "playwright": "1.63.0"
  }
}

There is no web framework, no database and no settings file. Nothing has asked for them yet. Each tool enters the project in the lesson where a test first needs it.

Question 7What happens when we run it?

Predict before you look

We have a test, and no app at all. We run bun test. Will it pass, fail, or refuse to run? And what will the message say?

Show the result 
error: Script not found "start"
error: Featherbase did not start at http://localhost:3210

 0 pass
 1 fail

It fails, and it fails for the right reason. The second line is our own message, from waitUntilFeatherbaseAnswers. There is nothing to start, so nothing answers.

Wait. If bun test works, why does bun start not?

bun test is built into Bun. It finds every file ending in .test.ts and runs it.

bun start is not built in. It means "run the script named start in package.json". Ours has no scripts yet, so Bun says "Script not found". Creating it is the job of the next lesson.

Question 8Why would anyone save a failing test?

We commit now, while the test is failing. The commit message starts with the word red:.

  • A test that has never failed proves nothing. It might pass for the wrong reason. Seeing it fail first shows that it can tell "missing" from "present".
  • The failure is the to-do list. It says exactly what to build next: something that answers when we run bun start.
  • The history becomes a lesson. Anyone can go back to this commit, run the test and watch it fail.

Try it yourself

git checkout b35d387
bun install
bunx playwright install chromium
bun test

You should see the two error lines above. If you do, you have reproduced a red.

Check yourselfAnswer, then open each one

What is an acceptance criterion?

One plain sentence saying what must be true for the work to be accepted. Here: opening Featherbase shows "Welcome to Featherbase".

Name two of the three simpler ways to test the page, and how each one bites later.

Calling the page's code directly tests the inside and proves nothing about starting. Asking the app with no browser cannot see what a browser does. Fetching from the started program is still blind to the browser.

Why does the test knock on the address in a loop instead of opening the page straight away?

Starting a program returns before the program is ready to answer. Knocking every 100 milliseconds waits exactly as long as needed, and gives up with a clear message after 3 seconds.

What does fetch(address).then(() => true, () => false) give back when nothing is listening?

false. The failure is turned into an ordinary answer, so the waiting loop can simply try again.

Why did we install only Playwright?

It is the only outside tool the test imports. A tool enters when a test needs it, not before.

Why commit while the test is failing?

To prove the test can fail, to let the failure say what to build next, and so anyone can replay it from the history.

In your own words: why are there no comments in the test file?

Small functions with clear names say what each step does, so the top of the file reads like a table of contents.
