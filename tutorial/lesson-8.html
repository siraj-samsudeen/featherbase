Proving the front door

Two lines of our project are checked by nothing: the file that starts Featherbase. This lesson tests it, and deals honestly with a test that passes the first time it is run.

Which file was missing from the coverage table, and why?

start.ts. No test loads it, so it is not measured.

What should you do before trusting a safety check?

See it fail. Break something on purpose and watch the check catch it.

Question 1What is the gap?

start.ts is two lines, and package.json has one line that points at it. A typo in either would pass every test and the coverage gate, and would be found only when someone tries to run Featherbase. It is the one command every person and every deployment depends on.

Question 2What are the options?

A. Leave it

Two lines, rarely touched.

Bites later: the most important command is the only thing with no proof.

B. One test that runs the real bun start and asks for the home page We chose this

No browser. Start the program, wait until it answers, check the welcome words.

Costs: the wait loop from lesson 1 comes back, but only here, where a separate program really does take a moment to start.

C. Let the deployment catch it

No work now.

Bites later: that is the most expensive place to find a typo.

Question 3Where does the criterion go?

It is not about the Home page. So it gets its own small folder, named for the action:

# Starting

The scene: someone runs Featherbase.

## Acceptance criteria

1. Running `bun start` opens Featherbase on the port it is given.

"The port it is given" is how a hosting service tells a program where to listen.

Question 4What does the test look like?

features/foundations/starting/starting.test.ts

import { afterAll, expect, test } from "bun:test";

let featherbase: ReturnType<typeof Bun.spawn> | undefined;

afterAll(() => {
  stopFeatherbase();
});

test("Running `bun start` opens Featherbase on the port it is given.", async () => {
  const port = aFreePort();
  runBunStartOn(port);
  const page = await pageOnceItAnswers(`http://localhost:${port}`);
  expect(page).toContain("Welcome to Featherbase");
});

Four lines tell the story: get a free port, run bun start on it, fetch the page once it answers, expect the welcome words.

Show me the helpers
function aFreePort() {
  const probe = Bun.serve({ port: 0, fetch: () => new Response() });
  const port = probe.port;
  probe.stop(true);
  return port;
}

function runBunStartOn(port: number | undefined) {
  featherbase = Bun.spawn(["bun", "start"], {
    env: { ...process.env, PORT: String(port) },
    stdout: "ignore",
    stderr: "ignore",
  });
}

async function pageOnceItAnswers(address: string) {
  const giveUpAt = Date.now() + 3000;
  while (true) {
    const page = await fetch(address).then(
      (response) => response.text(),
      () => undefined,
    );
    if (page !== undefined) return page;
    if (Date.now() > giveUpAt) throw new Error(`bun start did not open Featherbase at ${address}`);
    await Bun.sleep(50);
  }
}

function stopFeatherbase() {
  featherbase?.kill();
}

aFreePort opens a throwaway server on "any port", notes which port the computer chose, and closes it.

Why is there no beforeAll here, when the other test file has one?

In the Home tests, starting Featherbase is preparation that two tests share, and neither test is about starting. Here, starting is the very thing being tested. Hidden in beforeAll, the test body would have nothing left to say.

Question 5It passed the first time. Is that a problem?

Stop and guess first

Every earlier test was seen failing before it passed. This one passed on its first run, because the code it checks already existed. Can we trust it? What would you do?

A test that has never failed proves nothing by itself. So we make it fail on purpose.

A typo in start.ts, lisen for listen:

error: bun start did not open Featherbase at http://localhost:39035
 2 pass
 1 fail

A typo in the start line of package.json gives the same failure. With both restored, all three tests pass. Now the test has earned its trust.

There is no red commit this time, and the history says so honestly: the commit starts with test:, meaning a test added for code that already existed, shown to fail when that code is broken.

Question 6Why not stop the program right at the end of the test?

It is a natural question. The test starts the program, so why does a separate afterAll stop it? Because of what happens on failure. If these were the last two lines:

  expect(page).toContain("Welcome to Featherbase");
  stopFeatherbase();

and the expect fails, the test ends at that line. The stop never runs, and a stray Featherbase keeps running on the machine. afterAll runs whether the test passed or failed.

But there is a way to keep start and stop together and still be safe:

test("Running `bun start` opens Featherbase on the port it is given.", async () => {
  const port = aFreePort();
  const featherbase = runBunStartOn(port);
  try {
    const page = await pageOnceItAnswers(`http://localhost:${port}`);
    expect(page).toContain("Welcome to Featherbase");
  } finally {
    featherbase.kill();
  }
});

try ... finally means: do this part, and whatever happens, pass or fail, do the finally part afterwards. For this, runBunStartOn hands back the program it started, by saying return Bun.spawn(...). The variable at the top of the file, the afterAll block and stopFeatherbase all disappear. This became a small refactor: commit.

Which is better? It depends on who owns the thing being cleaned up. One test owns this program, so the clean-up sits inside that test. In the Home tests, two tests share one browser, so beforeAll and afterAll still fit there.

The habit to take away

Whatever a test starts, it must stop, even when it fails. Put the clean-up where failure cannot skip it, and as close to the start as sharing allows.

A step further

The honest gap that remains: the default port, 3000, is untested, because it may be busy on any machine that runs the suite. Name such gaps in writing. An acknowledged gap is a decision. An unnoticed one is a bug waiting.

Why was a typo in start.ts invisible to every check before this lesson?

No test loaded the file, and coverage only measures files the tests load.

What do you do with a test that passes the first time it is run?

Break the code on purpose and confirm the test fails, then restore it.

What does a test: commit tell the reader?

A test was added for code that already existed, and was shown to fail when that code is broken.

Why is stopping the program on the line after expect unsafe?

If the expect fails, the test ends there and the stop never runs.

When is try ... finally the better fit, and when afterAll?

try ... finally when one test owns what it started. afterAll when several tests share it.
