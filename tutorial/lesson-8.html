A gate that says no

Measuring is not enforcing. This lesson makes the test run fail whenever any line is unproven, and shows how to prove that a setting works when there is nothing to write a test about.

Commit: choreAbout 7 minutes

From the last lessonAnswer, then open each one

Why can coverage see our code now?

The tests build the app and start it inside their own program, which is the program Bun measures.

What does a missing file in a coverage report mean?

No test loaded it. It is unmeasured, which is a gap, not a pass.

Question 1What is a gate?

A gate is a check that fails the whole run when a rule is broken. Our rule: coverage must be 100%. With a gate, an unproven line cannot slip in quietly. The only two ways forward are to write a criterion and test for that line, or to delete it.

Question 2What are the ways to build one?

A. The gate built into Bun We chose this

Three lines in a settings file. No code of ours.

Bites later: when it fails, no sentence says why. You see "0 fail" and a failed run, and must spot the percentage in the table yourself.

B. Our own small script

It runs the tests, reads the report and prints a plain line naming the file and lines.

Costs: about 40 lines of our own code, which then need their own criteria and tests.

We chose A, the least thing that gives a real gate, and wrote down its weakness. If the silent failure ever confuses someone, that is the felt need that justifies B.

Question 3What is the setting?

bunfig.toml

[test]
coverage = true
coverageThreshold = 1.0
  • bunfig.toml is Bun's settings file. [test] means these apply to bun test.
  • coverage = true measures on every run, with nothing extra to type.
  • coverageThreshold = 1.0 means 100%. Anything less fails the run.

Question 4How do you prove a setting works?

A settings file has no behaviour of the product to write a criterion about. So we do not invent a test. We prove it by hand, in three moves, and show the evidence.

Move 1. Without the gate, add a function nobody calls

export function nobodyCallsThis() {
  return "unproven";
}
 2 pass
 0 fail

The run passes. That is the problem we are solving.

Move 2. Add the three lines and run again

File            | % Funcs | % Lines | Uncovered Line #s
All files       |   75.00 |   84.62 |
 featherbase.ts |   75.00 |   84.62 | 16-17

 2 pass
 0 fail

Now the run is marked failed, and lines 16-17 are exactly the function we added.

Move 3. Remove the function

All files       |  100.00 |  100.00 |

 2 pass
 0 fail

Only the settings file is committed, as chore:. That word marks a change to the project's tooling, not to what the product does. The throwaway function never enters the history.

The habit to take away

Never trust a safety check you have not seen fail. Break something on purpose, watch the check catch it, then undo the break.

A step further

100% line and function coverage is a floor, not a proof of correctness. Its real value under this workflow is as a detector of code nobody asked for. Treat a coverage failure as "which criterion is missing, or which code should go?"

Try it yourself

git checkout 5f85d70 && bun install
printf '\nexport function nobodyCallsThis() {\n  return 1;\n}\n' >> featherbase.ts
bun test; echo "exit code: $?"
git checkout featherbase.ts

The exit code is 1, which is how a program says "I failed". The last line removes your experiment.

Check yourselfAnswer, then open each one

What is the difference between measuring coverage and gating on it?

Measuring reports the number. A gate fails the run when the number is below the rule.

What are the only two answers when the gate fails?

Write a criterion and test for the unproven code, or delete the code.

What is the weakness of Bun's built-in gate?

It fails without a sentence saying why. You have to read the table.

How did we prove the gate works without writing a test?

Added an uncalled function: passed without the gate, failed with it, passed again once removed.

What does a chore: commit mean?

A change to the project's tooling or settings, not to the product's behaviour.
