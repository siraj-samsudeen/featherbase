A second behaviour: page not found

We found a flaw: every address shows the welcome page. This lesson fixes it the disciplined way. First the sentence, then a failing test, then the fix.

Before you start: recall the last lesson

Answer from memory first, then open each one. A little effort here is what moves it into long-term memory.

What flaw did the last lesson leave in on purpose?

The program answers every address with the welcome page.

What should you do when you spot a flaw during a green step?

Do not fix it. Write it down as the next criterion so it gets its own test.

Question 1What is the new criterion?

We add one line to the same file as before:

features/foundations/home/home.md

## Acceptance criteria

1. Opening Featherbase shows "Welcome to Featherbase".
2. Opening an address Featherbase does not have shows "Page not found".

A good not-found page does two things. It shows words a person can read, and it sends a number that browsers and tools understand: 404. Every web answer carries such a number, called a status. 200 means "fine". 404 means "there is nothing at this address".

Question 2What does the failing test look like?

features/foundations/home/home.test.ts

test('Opening an address Featherbase does not have shows "Page not found".', async () => {
  const visit = await openInNewTab("/no-such-page");
  expect(visit.status).toBe(404);
  expect(await textOn(visit.page)).toContain("Page not found");
});

One helper had to grow to serve both tests. It used to open only the home address. Now it takes the address to open, and also hands back the status:

async function openInNewTab(path: string) {
  const page = await browser.newPage();
  const response = await page.goto(address + path);
  return { page, status: response?.status() };
}

Question 3What is the least fix?

One decision: is this the home address? If yes, the welcome page. If no, a not-found page with 404.

start.ts

const welcomePage = "<!doctype html><title>Featherbase</title><h1>Welcome to Featherbase</h1>";
const notFoundPage = "<!doctype html><title>Page not found</title><h1>Page not found</h1>";

Bun.serve({
  port: Number(process.env.PORT ?? 3000),
  fetch: (request) => (isHomeAddress(request) ? html(welcomePage) : html(notFoundPage, 404)),
});

function isHomeAddress(request: Request) {
  return new URL(request.url).pathname === "/";
}

function html(page: string, status = 200) {
  return new Response(page, { status, headers: { "content-type": "text/html; charset=utf-8" } });
}

The fetch line now reads as the decision itself. isHomeAddress is one line, and it still gets a name, because the name says what the line means.

 2 pass
 0 fail

We commit this as green:.

Question 4Why two commits and not one?

Because each commit should do one thing you can name. The red commit says "here is a behaviour we lack". The green commit says "here is the least change that provides it". If something breaks later, the history tells you exactly which step to look at.

If you have done this before

Note the test asserts the status and the text. Asserting only the text would pass against a 200 page that happens to say "Page not found", which is the classic soft-404 bug.

Try it yourself

git checkout 6506af3

You have now replayed a full red and green by hand.

Check yourselfClose your eyes and answer, then open each one

What does status 404 mean, and what does 200 mean?

404: nothing at this address. 200: fine.

Why does the test check the status as well as the words?

A page could say "Page not found" while still reporting 200. Tools and browsers rely on the number.

In what order did we work?

The criterion in the .md file, then the failing test (red), then the least fix (green).

Why give a one-line function like isHomeAddress a name?

The name says what the line means, so the place that uses it reads like plain language.
