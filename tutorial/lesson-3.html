A second behaviour: page not found

We found a flaw: every address shows the welcome page. Before fixing it, we write down what should happen instead, and a test that fails until it does.

What flaw did the last lesson leave in on purpose?

The program answers every address with the welcome page.

What should you do when you spot a flaw during a green step?

Do not fix it. Write it down as the next criterion so it gets its own test.

Question 1What is the new criterion?

We add one line to the same file as before:

features/foundations/home/home.md

## Acceptance criteria

1. Opening Featherbase shows "Welcome to Featherbase".
2. Opening an address Featherbase does not have shows "Page not found".

A good not-found page does two things. It shows words a person can read, and it sends a number that browsers and tools understand: 404. Every web answer carries such a number, called a status. 200 means "fine". 404 means "there is nothing at this address".

Question 2What should the test check?

1. Only the words "Page not found"

The simplest check, and it reads exactly like the sentence.

Bites later: the number could still say 200, "fine". Browsers, search engines and monitoring tools read the number, not the words, so they would treat the page as real. A page that says "not found" while its number says "fine" is a well-known bug called a soft 404.

2. Only the number 404

Every tool is happy.

Bites later: a person could still get a blank or confusing page.

3. Both We chose this

The person sees the words; the tools get the number.

Costs: one more line in the test.

We also had to choose which wrong address to try. One example is enough for now: /no-such-page. A deeper one comes back much later, when a person opens a Table that does not exist.

Question 3What does the failing test look like?

features/foundations/home/home.test.ts

test('Opening an address Featherbase does not have shows "Page not found".', async () => {
  const visit = await openInNewTab("/no-such-page");
  expect(visit.status).toBe(404);
  expect(await textOn(visit.page)).toContain("Page not found");
});
  • openInNewTab("/no-such-page") opens a made-up address in a new tab.
  • visit.status is the number the server sent back. visit.page is the tab, so we can read its words.
  • The number is checked first. That decides which failure we see, as you will find out below.

To make room for this test, a helper had to grow. It used to open only the home address. Now it takes the address to open, and also hands back the number:

async function openInNewTab(path: string) {
  const page = await browser.newPage();
  const response = await page.goto(address + path);
  return { page, status: response?.status() };
}
  • The address. path is the part after the server's name, such as / or /no-such-page.
  • The answer. page.goto hands back the server's response. Before, we threw it away; now we keep it, to read its number.
  • The guard. response?.status(): the ?. means "only if there is a response". In a few rare cases, such as jumping to a spot further down the same page, goto hands back nothing.
  • Two things at once. { page, status } bundles the tab and the number into one object, so the test can use either.

Because the helper changed, the first test changed too: it now calls openInNewTab("/"). What it expects is the same.

A step further

In the strictest red, green, refactor, reshaping a helper is its own refactor commit, made before the red. Here it is folded into the red commit because it is tiny. Worth knowing when you read "red" as "only a new failing test".

Question 4Does it fail, and for the right reason?

Predict before you look

We run both tests against the program from lesson 2. Which pass, which fail, and what will the failing one report?

Expected: 404
Received: 200
(fail) Opening an address Featherbase does not have shows "Page not found".

The first test still passes, so reshaping the helper broke nothing. The new one shows the program answering 200, "fine", for a page that does not exist. That is our flaw, now caught by a test. We commit this as red:.

Why does the failure talk about the number and not the words?

Because the number is checked first, and a test stops at its first failed check. Had the words been checked first, the message would have been that the welcome page does not contain "Page not found". That is true, but it says less about the cause. Put the check that names the cause most sharply first.

The habit to take away

A red only counts if it fails for the reason you predicted. Read the failure before you write any fix.

A step further

The test checks for 404, but the sentence in home.md never mentions it. A test that checks more than its sentence says is a quiet requirement: nobody reading only the sentences would know about it. When we reviewed this step, we decided the sentence should say "with status 404", so that the promise is written where people read promises.

What does status 404 mean, and what does 200 mean?

404: nothing at this address. 200: fine.

What is a soft 404?

A page that says "not found" in words while its number says 200, "fine". Tools that read the number treat it as a real page.

Why does the test check the number before the words?

A test stops at its first failed check, so the first check decides the message. The number names the cause most sharply.

What does ?. do in response?.status()?

It asks for the status only if there is a response. Without it, a missing response would crash the helper.
