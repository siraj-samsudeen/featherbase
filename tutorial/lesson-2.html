The least code that passes

The test is failing because nothing starts. In this lesson we write the smallest program that makes it pass, and we resist writing anything more.

What did the failing test say was missing?

Nothing answered when the test ran bun start. The message was "Featherbase did not start".

Why did we commit while the test was failing?

To prove the test can fail, and so the failure tells us exactly what to build next.

Question 1What does "green" mean?

Green is the step where you write the least code that turns the failing test into a passing one. Not the best code. Not the code you know you will need next week. Only what this one failure asks for.

It feels wrong at first. You can see the future, so why not build for it? Because every line you add beyond the test is a line that nothing proves.

Question 2What are the ways to make something answer?

1. A plain HTML file, and no program

Bun can serve an .html file directly. No code at all.

Bites later: it is a preview server for fixed pages. It cannot read a database or decide what to show. It would be thrown away at the very next criterion.

2. The web server built into Bun We chose this

A few lines that answer a request with the page. No package to install.

Costs: for many pages you would hand-write what a framework gives you. We will feel that soon.

3. A web framework

It is where a real project ends up.

Why not now: nothing in this test needs it yet. A tool comes in when a test needs it.

Question 3What do we write?

One new file. Read it top to bottom.

start.ts

const welcomePage = "<!doctype html><title>Featherbase</title><h1>Welcome to Featherbase</h1>";

Bun.serve({
  port: Number(process.env.PORT ?? 3000),
  fetch: () => html(welcomePage),
});

function html(page: string) {
  return new Response(page, { headers: { "content-type": "text/html; charset=utf-8" } });
}
  • welcomePage is the page itself: a title for the browser tab and one heading.
  • Bun.serve starts the server. port is the one the test passes in, or 3000 when you run it yourself.
  • fetch runs for every request and answers with the welcome page.
  • html(...) labels the answer as HTML, so the browser shows a heading and not raw text.

And one addition to package.json, so that the command bun start exists:

package.json

"scripts": {
  "start": "bun start.ts"
},
Why does the test run bun start and not bun start.ts?

Because bun start is what a person would type, and by convention every project answers to it. The test then proves the real way in. If the file is renamed later, only that one line in package.json changes and the test stays as it is.

Question 4Does it pass?

It passes. And the answer to the prediction: it shows the welcome page for every address. That is sloppy, and deliberately so. No criterion has asked for anything else yet. Lesson 3 is where a test forces us to fix it.

The habit to take away

When you spot a flaw during a green step, do not fix it. Write it down as the next criterion. The flaw then gets a test of its own, and you never change behaviour without proof.

If you have done this before

This is "fake it till you make it" taken seriously. The deliberately wrong generalisation, answering every path, is what makes the next red meaningful instead of ceremonial.

What is the one rule of a green step?

Write the least code that makes the failing test pass, and nothing more.

Why did we not install a web framework?

Nothing in the test needed it. Bun's built-in server was enough.

What flaw did we leave in on purpose, and what do we do about it?

Every address shows the welcome page. We do not fix it now. It becomes the next criterion, with its own failing test.

What does the scripts section of package.json do?

It gives names to commands. bun start runs the script named start.
