The least code that passes

The test is failing because nothing starts. In this lesson we write the smallest program that makes it pass, and we resist writing anything more.

What did the failing test say was missing?

Nothing answered when the test ran bun start. The message was "Featherbase did not start".

Why did we commit while the test was failing?

To prove the test can fail, and so the failure tells us exactly what to build next.

Question 1What does "green" mean?

Green is the step where you write the least code that turns the failing test into a passing one. Not the best code. Not the code you know you will need next week. Only what this one failure asks for.

It feels wrong at first. You can see the future, so why not build for it? Because every line you add beyond the test is a line that nothing proves.

Question 2What are the ways to make something answer?

1. A plain HTML file, and no program

Bun can serve an .html file directly. No code at all.

Bites later: it is a preview server for fixed pages. It cannot read a database or decide what to show. It would be thrown away at the very next criterion.

2. The web server built into Bun We chose this

A few lines that answer a request with the page. No package to install.

Costs: for many pages you would hand-write what a framework gives you. We will feel that soon.

3. A web framework

It is where a real project ends up.

Why not now: nothing in this test needs it yet. A tool comes in when a test needs it.

Question 3What do we write?

One new file. Read it top to bottom.

start.ts

const welcomePage = "<!doctype html><title>Featherbase</title><h1>Welcome to Featherbase</h1>";

Bun.serve({
  port: Number(process.env.PORT ?? 3000),
  fetch: () => html(welcomePage),
});

function html(page: string) {
  return new Response(page, { headers: { "content-type": "text/html; charset=utf-8" } });
}
  • welcomePage is the page itself: a title for the browser tab and one heading.
  • Bun.serve starts the server. port is the one the test passes in, or 3000 when you run it yourself.
  • fetch runs for every request and answers with the welcome page.
  • html(...) labels the answer as HTML, so the browser shows a heading and not raw text.

And one addition to package.json, so that the command bun start exists:

package.json

"scripts": {
  "start": "bun start.ts"
},
Why does the test run bun start and not bun start.ts?

Because bun start is what a person would type, and by convention every project answers to it. The test then proves the real way in. If the file is renamed later, only that one line in package.json changes and the test stays as it is.

Question 4How does each piece work?

A request comes in, Bun hands it to our function, and our function hands back an answer:

browser ── "GET /" ──►  Bun.serve, listening at door number PORT
                          │
                          ▼
                       fetch(request)      our function, run once per request
                          │
                          ▼
browser ◄── Response ──  body:          the page
                         status:        200, "fine"
                         content-type:  text/html; charset=utf-8
  • Starting. Bun.serve({...}) is the web server built into Bun. Calling it starts listening at once, and the program then keeps running, waiting for requests, until something stops it.
  • The port. A port is a door number on the computer. process.env.PORT reads a setting called PORT from outside the program: the test sets it to 3210, and hosting services set it too. ?? 3000 means "if no one set it, use 3000". Number(...) turns the text "3210" into the number 3210, because settings like this always arrive as text.
  • Answering. fetch is the function Bun calls for every request. It is given the request and must give back a response. Ours, () => html(welcomePage), takes no input at all: the empty () means it never looks at the request, so every address gets the same page. The name mirrors the browser's own fetch(). The browser's turns a request into a response by asking; the server's turns a request into a response by making one.
  • The answer. new Response(page, {...}) builds the reply. It is the same Response the browser's fetch() hands you, a standard shape every modern server understands. page is the body, the words actually sent. No status is given, so it is 200, "fine". Lesson 3 is where we first need another one.
  • The label. headers are labels sent ahead of the body. text/html tells the browser "draw this as a web page". charset=utf-8 says how the letters were turned into bytes; without it, a name with an accent, Tamil script or ₹ can come out garbled.

Think of a shop counter. Bun.serve opens the shop at door number PORT. fetch is the person behind the counter, and for now they hand every customer the same leaflet, whatever they asked for.

Question 5Why say "HTML" twice?

The page starts with <!doctype html>, and the label says text/html. It looks like saying the same thing twice. It is not: the two answer different questions, at different moments.

server ──[ label: content-type ]──► browser: "what kind of file is this?"
                                     HTML ▼            plain text ▼
                         reads <!doctype html>:     shows the raw characters
                         "which rules do I draw by?"
  • content-type arrives before the page and decides whether the browser treats it as HTML at all.
  • doctype is read only once the browser knows it is HTML. It picks the drawing rules: today's standard ("standards mode"), or, without it, "quirks mode", which copies the bugs of late-1990s browsers so that very old sites still look as they did.

We tried all three in a real browser:

both             text/html    standards mode
                 shows: Welcome to Featherbase
no doctype       text/html    quirks mode
                 shows: Welcome to Featherbase
no content-type  text/plain   a text file
                 shows: <!doctype html>…<h1>Welcome to Featherbase</h1>

Drop the doctype and nothing looks different today, but layouts start behaving oddly once the design's styling arrives. Drop the label and Bun calls the body plain text, so the browser shows the tags themselves. Each line does a job the other cannot.

A step further

Look at the last row again: the words "Welcome to Featherbase" are still in its text. Our test asks toContain, so it would pass on that broken page. Checking the words a person sees is the right habit, but toContain is generous. Later tests ask the page for a heading or a button by its role, which would catch this.

Question 6Does it pass?

Predict before you look

Look at the fetch line again. What will this program answer if you open an address that does not exist, such as /no-such-page?

Show the result
 1 pass
 0 fail
error: script "start" was terminated by signal SIGTERM (Polite quit request)

It passes. And the answer to the prediction: it shows the welcome page for every address. That is sloppy, and deliberately so. No criterion has asked for anything else yet. Lesson 3 is where a test forces us to fix it.

The last line says error. Did something break?

No. The test had already passed. That line is the test cleaning up after itself:

test ──starts──► bun start ──starts──► bun start.ts
                 (the script)          (the server)
     ──SIGTERM, "please quit"────────► server quits
                 bun start reports:
                 "script start was terminated by signal SIGTERM"

When the test ends, featherbase.kill() sends the server a polite "please quit" signal called SIGTERM. The server quits, and bun start, which started it, reports that its program was stopped by a signal. It is a report, not a failure.

There are four ways to make it go away:

1. Start the server inside the test's own program

No second program, so nothing is stopped by a signal. Faster, and no waiting loop.

Costs: it no longer proves that bun start works for a person.

2. Run bun start.ts instead of bun start

One word, and the line is gone.

Bites later: a typo in the start script in package.json would go unnoticed.

3. Keep bun start, and switch off its messages

Still proves the real command.

Costs: it hides real error messages too. If Featherbase crashed while starting, you would see only "did not start", not why.

4. Teach the server to hear SIGTERM and finish cleanly

Hosting services send SIGTERM on every deploy, so a server that finishes its open requests before quitting is worth having one day.

Why not now: no criterion asks for it.

We end up using two of them together. Lesson 6 takes the first: the tests start Featherbase inside their own program. Lesson 8 keeps one test that still runs the real bun start, with its messages switched off, so the front door is still proved.

Why not answer only the home address right now? That is the address the test opens.

Because the other half of that decision has no test. Matching / forces a choice for every other address:

fetch: (request) =>
  new URL(request.url).pathname === "/" ? html(welcomePage) : ???

Whatever goes in ??? (a 404, an empty page, an error) is behaviour no criterion has asked for, so nothing would check it. It could be wrong and still pass. The next criterion, "an address Featherbase does not have shows Page not found", is what makes the check necessary, and it arrives together with the test for its other half.

Many developers would write the check now, and that is a fair choice. We take the stricter road, so that every line has a test that asked for it.

The habit to take away

When you spot a flaw during a green step, do not fix it. Write it down as the next criterion. The flaw then gets a test of its own, and you never change behaviour without proof.

A step further

This is "fake it till you make it" taken seriously. The deliberately wrong generalisation, answering every path, is what makes the next red meaningful instead of ceremonial.

Check yourselfAnswer, then open each one

What is the one rule of a green step?

Write the least code that makes the failing test pass, and nothing more.

Why did we not install a web framework?

Nothing in the test needed it. Bun's built-in server was enough.

What flaw did we leave in on purpose, and what do we do about it?

Every address shows the welcome page. We do not fix it now. It becomes the next criterion, with its own failing test.

What does the scripts section of package.json do?

It gives names to commands. bun start runs the script named start.

What does the empty () in fetch: () => html(welcomePage) tell you?

The function never looks at the request, so every address gets the same page.

Why does the page need both <!doctype html> and the text/html label?

The label decides whether the browser treats the answer as HTML at all. The doctype decides which drawing rules it uses. Drop the label and you see raw tags; drop the doctype and the page is drawn by 1990s rules.

The run ends with error: script "start" was terminated by signal SIGTERM. What happened?

The test politely stopped the server it had started, and bun start reported it. The test had already passed; it is not a failure.
