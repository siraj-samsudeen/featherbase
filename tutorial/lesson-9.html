A machine that never forgets

Every check so far runs only when a person runs it. This last lesson hands the job to GitHub, so that every push is tested on a clean machine without anyone remembering.

Name the kinds of commit this series has used.

red: a failing test. green: the least code that passes. refactor: same behaviour, built differently. chore: tooling. test: a test for code that already existed.

What must a test do with anything it starts?

Stop it, even when the test fails.

Question 1What is CI?

CI stands for continuous integration. In plain words: a service runs your checks by itself every time code is pushed, on a fresh machine, and marks the result green or red next to the commit.

It catches two things a person cannot. "It works on my machine", because the fresh machine has nothing of yours on it. And forgetting, because it never does.

Question 2What should it run?

A. Only bun test We chose this

Exactly what we have proven by hand. The coverage gate comes along, since it is part of bun test.

Costs: none yet. Other checks can join later.

B. A plus a type check

It would catch wrong types, which Bun does not check when running TypeScript.

Why not now: nothing has bitten us yet, so it waits for a felt need.

Each further check joins CI in the same commit that creates it.

Question 3What does the file say?

.github/workflows/checks.yml

name: Checks

on: push

jobs:
  tests:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: 1.4.4
      - run: bun install --frozen-lockfile
      - run: bunx playwright install --with-deps chromium
      - run: bun test
  • on: push: run this every time anything is pushed.
  • runs-on: ubuntu-latest: a fresh Linux machine each time.
  • timeout-minutes: 10: stop a stuck run.
  • The steps: fetch the code, install Bun at our version, install our packages exactly as recorded, install the Chromium browser, then run the tests.
What does --frozen-lockfile mean?

When you install packages, Bun records the exact versions in a file called bun.lock. --frozen-lockfile says: install exactly those, and fail if that is not possible. So the clean machine tests the same versions you tested.

Predict before you look

Our history contains red: commits, which fail on purpose. Will CI mark the project as broken because of them?

Show the answer

No. CI runs on the newest commit of each push. A red commit in the middle of the history is never the newest one once its green follows. The red commits remain there for anyone to check out and learn from.

The habit to take away

If a check matters, a machine should run it. Rules that depend on people remembering get forgotten on exactly the day they are needed.

The whole journeyWhat did these lessons build?

Very little product: one page that says welcome, and one that says not found. But around it, a way of working:

  1. Say what must be true, in one plain sentence, before any code.
  2. Write the test first and watch it fail.
  3. Write the least code that passes.
  4. Improve the code with the tests standing guard.
  5. Bring in each tool only when its absence hurts.
  6. Before every choice, lay out the options and what each will cost later.
  7. Never trust a check you have not seen fail.
  8. Hand the checks to a machine.

What two problems does CI catch that a careful person cannot?

"Works on my machine", and forgetting to run the checks.

Why do the red commits not break CI?

CI judges the newest commit of a push, and a red is always followed by its green.

What does --frozen-lockfile guarantee?

The clean machine installs exactly the versions recorded in bun.lock.
