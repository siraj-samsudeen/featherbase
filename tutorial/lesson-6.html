Asking what the tool already does

We brought in a framework, but we still label every page ourselves. This lesson asks what the tool can already do, removes our helper, and looks at what the change really cost.

What three facts prove a change was a refactor?

Tests passed before, the tests were not touched, and the tests pass after.

What did Elysia replace?

Our hand-written check of the address. .get("/", ...) now does the matching, and Elysia raises NOT_FOUND for everything else.

Question 1Is that the best we can do with this tool?

Stop and think

Look at the html(...) helper. We wrote it ourselves back in lesson 2. Now that we use a framework, what question should we ask about it?

The question is: does the tool already do this? It is worth asking every time you adopt one. Here, the answer was found by trying, not by remembering:

  • Elysia alone labels data by itself, but not HTML.
  • Elysia's own official add-on, @elysiajs/html, recognises a page and labels it.

Question 2What are the ways to label a page?

1. Keep our own three-line helper

It works, and it needs no package.

Costs: it repeats what the framework's add-on does, and every handler must remember to wrap its page.

2. Set the label by hand in each handler

Elysia lets a handler set any header itself.

Bites later: even more repetition than the helper, one line per page.

3. Elysia's official HTML add-on We chose this

Switched on once, and every page is labelled. It is also the door to writing pages as JSX later.

Costs: more than the diff shows. Question 4 counts it.

Question 3What does the second swap look like?

start.ts

import { html } from "@elysiajs/html";
import { Elysia } from "elysia";

const welcomePage = "<!doctype html><title>Featherbase</title><h1>Welcome to Featherbase</h1>";
const notFoundPage = "<!doctype html><title>Page not found</title><h1>Page not found</h1>";

new Elysia()
  .use(html())
  .get("/", () => welcomePage)
  .onError(({ code }) => {
    if (code === "NOT_FOUND") return notFoundPage;
  })
  .listen(Number(process.env.PORT ?? 3000));
  • Switched on once. .use(html()) turns the add-on on for every route.
  • Plain strings. The handlers return the page text itself. No new Response, and no 404 written anywhere: Elysia keeps the status of its own NOT_FOUND error.
  • Our helper is gone, and with it the status = 200 default from lesson 4.
test and criteria files changed:  none

Tests untouched, both pass. A second refactor: commit.

Question 4What did the add-on bring with it?

We deleted three lines. bun.lock gained 22 entries, more than the whole framework brought in lesson 5:

@elysiajs/html                  the add-on (its peer: elysia, ours)
├─ @kitajs/html                 writes pages as JSX on the server
│   └─ csstype                  types for style="..." values
└─ @kitajs/ts-html-plugin       "xss-scan": flags unsafe values in JSX
    ├─ typescript               a required peer, so Bun installed it
    ├─ tslib, chalk             TypeScript helpers; coloured terminal text
    └─ yargs                    reads command-line options
        ├─ yargs-parser, y18n, escalade, get-caller-file
        ├─ string-width 8.3.0 ─ get-east-asian-width, strip-ansi ─ ansi-regex
        └─ cliui
            ├─ string-width 7.2.0 ─ emoji-regex
            └─ wrap-ansi ─ ansi-styles, string-width 7.2.0
  • Two packages do the real work. @kitajs/html is the engine for JSX pages. @kitajs/ts-html-plugin is a checker you run from the command line, and everything below it exists so that a command-line tool can print coloured, well-wrapped output.
  • Lesson 5's rule at work. The checker lists typescript as a required peer, so Bun installed the whole TypeScript compiler.
  • Two versions of one package. yargs wants string-width 8 and cliui wants 7, so both are kept, each where it is needed. That is why bun.lock lists it twice.
A step further

A refactor that removes code can still add a lot. The lock-file diff is part of a change's real size, even though most review tools fold it away.

Question 5How does the add-on know a string is a page?

It guesses. We asked the real server, then changed the welcome page to plain words and asked again:

page starts with "<!doctype"   GET /  200  text/html; charset=utf8
page is "Welcome to ..."       GET /  200  text/plain;charset=utf-8

The add-on labels an answer as HTML only if its text starts with <. Ours do, so it works. A page that began with a space or with plain words would quietly go out as plain text, and the browser would show its tags.

The label's spelling also changed, from utf-8 to utf8. Browsers accept both, and no test checks it: a second small change the tests did not see, like the POST in lesson 5.

Question 6Could "page not found" have a name of its own?

Other frameworks give it one. They fall into three styles.

  • A file with a special name, no code: Rails, Django, Laravel, Next.js and Phoenix look for a page named for 404.
  • A named place for exactly this: Hono has notFound, Fastify has setNotFoundHandler, Flask has errorhandler(404).
  • One general error hook where you check what went wrong: Elysia and Express.

Here is the same page three ways.

1. Elysia, as committed

.onError(({ code }) => {
  if (code === "NOT_FOUND") return notFoundPage;
})

2. A tiny Elysia plug-in that gives it a name

function notFound(page: string) {
  return new Elysia({ name: "not-found" }).onError({ as: "global" }, ({ code, set }) => {
    if (code === "NOT_FOUND") {
      set.status = 404;
      return page;
    }
  });
}

new Elysia().use(html()).use(notFound(notFoundPage)).get("/", () => welcomePage);
  • { name: "not-found" } lets Elysia skip the plug-in if it is added twice.
  • { as: "global" } makes the hook apply to the whole app, not only to routes inside the plug-in.
  • set.status = 404 says the status out loud, instead of relying on Elysia to keep it.

We put this into start.ts and ran the real tests: 2 pass, 0 fail, with the same status and label as before.

3. Hono, which has the name built in

const app = new Hono();
app.get("/", (c) => c.html(welcomePage));
app.notFound((c) => c.html(notFoundPage, 404));

Hono's c.html(...) also labels the answer on purpose, where Elysia's add-on guesses from the first character. (This one is shown for comparison; it was not run.)

Keep Elysia's general hook for now We chose this

The plug-in reads better, .use(notFound(page)), and could be reused by every app later.

Why not now: nine lines to replace three, for one error page used once. When a second error page arrives, the plug-in's shape will be clear, and it is ready above.

The habit to take away

When you bring in a tool, ask twice. First: do I need it yet? Second, once it is in: what am I still doing by hand that it already does? Then look at what the answer costs.

Try it yourself

git checkout 4fcaf6c && bun install && bun test   # Elysia: 2 pass
git checkout d7022ca && bun install && bun test   # add-on: 2 pass
git diff 4fcaf6c d7022ca -- features/
git diff 4fcaf6c d7022ca --stat -- bun.lock

The first diff prints nothing: the tests did not change by a single character. The second shows how much the lock file grew.

What question should you ask right after adopting a tool?

What am I still doing by hand that the tool already does?

How does the HTML add-on decide that an answer is a page?

It looks at the first character. Text that starts with < is labelled HTML; anything else goes out as plain text.

Three lines were deleted. Why did bun.lock gain 22 entries?

The add-on brings a JSX engine and a command-line checker, and the checker brings TypeScript as a peer and a kit for printing in the terminal.

Why did we not write a named not-found helper?

Three lines used once. We wait for a second real use before extracting anything.
