Changing the tool without changing the behaviour

We hand-wrote address matching. Frameworks exist to do that. This lesson swaps the tool underneath while the tests stand guard, and that is what the word refactor means.

Commit: refactor (two of them)About 20 minutes

From the last lessonAnswer, then open each one

What are the three kinds of commit so far, and what does each do?

Red adds a failing test. Green adds the least code that passes it. Refactor, new in this lesson, changes how the code is built without changing what it does.

How did our program decide which page to show?

A hand-written check, isHomeAddress, compared the address with /.

Question 1What is a refactor, exactly?

A refactor changes how the code is built and nothing about what it does. The proof is simple and strict:

  • The tests pass before.
  • You do not touch the tests.
  • The tests pass after.

If you need to change a test, you are changing behaviour, and that is a red and green, not a refactor.

Question 2Which tool, and why now?

1. Stay on Bun's own server

Nothing to learn, no package.

Bites later: every new page means another hand-written address check. So do forms, sign-in and an API.

2. Elysia, a small web framework for Bun We chose this

You say "for this address, run this", once per address. It does the matching.

Costs: one more package to keep up to date.

3. A much bigger framework

More built in.

Why not: far more than a small server-rendered app needs.

Why now and not in lesson 2? Because now we have felt the need. One hand-written check was fine. The thought of fifty is what justifies the tool.

Question 3What does the first swap look like?

start.ts

import { Elysia } from "elysia";

const welcomePage = "<!doctype html><title>Featherbase</title><h1>Welcome to Featherbase</h1>";
const notFoundPage = "<!doctype html><title>Page not found</title><h1>Page not found</h1>";

new Elysia()
  .get("/", () => html(welcomePage))
  .onError(({ code }) => {
    if (code === "NOT_FOUND") return html(notFoundPage, 404);
  })
  .listen(Number(process.env.PORT ?? 3000));

function html(page: string, status = 200) {
  return new Response(page, { status, headers: { "content-type": "text/html; charset=utf-8" } });
}
  • .get("/", ...): when a browser asks for the home address, answer with the welcome page.
  • .onError(...) runs when something goes wrong. Elysia raises NOT_FOUND by itself for any address we did not define.
  • .listen(...) starts it.

isHomeAddress is gone. The tests were not touched, and both still pass. Commit: refactor:.

Did anything change that the tests do not check?

Yes, one thing. We sent the same requests to the server before and after the swap:

request             before (Bun.serve)   after (Elysia)
GET  /              200                  200
GET  /?from=email   200                  200
GET  /no-such-page  404                  404
POST /              200 welcome          404 not found
HEAD /              200                  200

A form sent to / (a POST) used to get the welcome page. Now it gets "Page not found", because .get matches only page requests. It is arguably better, but it shows what a refactor really promises: behaviour the tests check stays the same. Behaviour no test checks can drift without anyone noticing.

1 + 4 own + 3 peers + 9 under file-type = 17
  • The core is tiny. Elysia's own four helpers are small, because the actual web server is still Bun's. Elysia adds the matching and the shape of the code on top.
  • Elysia is built around describing data. TypeBox lets you write down what a request must contain; Elysia then checks every request against it and works out the TypeScript types from it.
  • Counting packages misleads. 9 of the 17 exist only so that file-type can recognise uploaded files. They cost nothing until something is uploaded.

Question 5What is a peer dependency, and why mark one?

A library can list another package in two ways:

A normal dependency

The library's private tool. It installs its own copy and you never touch it. memoirist, Elysia's router, is one: we never import it.

A peer dependency

"I work with this, but the project owns it, so there is exactly one copy and we share it." @sinclair/typebox is one.

A library marks a package as a peer for three reasons:

  • Objects cross the boundary. You build TypeBox descriptions in your code and hand them to Elysia. If each side had its own copy of TypeBox, Elysia's check "is this a TypeBox description?" could fail on yours, the types would not match, and the package would be installed twice.
  • A plug-in must plug into the one host. Elysia's HTML add-on, in the next question, lists elysia as its peer: it has to attach to our Elysia, not bring a second one.
  • The project chooses the version. The library states a range and the project picks within it. bun.lock shows Elysia's range for TypeBox: ">= 0.34.0 < 1".

Optional peers are used only if the project already has them. Here, typescript and @types/bun give the editor its type checks; the server runs without them.

Rule of thumb

If you will import a package yourself, or pass its objects to the library, it should be a peer. If only the library uses it, it is a normal dependency.

A step further

Bun, and npm from version 7, install required peers automatically. Older npm only printed a warning, "unmet peer dependency", and left you to install them, which is why that message is so familiar to anyone who used npm before 2021.

Question 6Is that the best we can do with this tool?

Stop and think

Look at the html(...) helper. We wrote it ourselves back in lesson 2. Now that we use a framework, what question should we ask about it?

The question is: does the tool already do this? It is worth asking every time you adopt one. Here, the answer was found by trying, not by remembering:

  • Elysia alone labels data by itself, but not HTML.
  • Elysia's own official add-on, @elysiajs/html, recognises a page and labels it.

So the helper was duplicating the tool. A second refactor removes it:

start.ts

import { html } from "@elysiajs/html";
import { Elysia } from "elysia";

const welcomePage = "<!doctype html><title>Featherbase</title><h1>Welcome to Featherbase</h1>";
const notFoundPage = "<!doctype html><title>Page not found</title><h1>Page not found</h1>";

new Elysia()
  .use(html())
  .get("/", () => welcomePage)
  .onError(({ code }) => {
    if (code === "NOT_FOUND") return notFoundPage;
  })
  .listen(Number(process.env.PORT ?? 3000));

Our own helper is gone completely. The not-found line no longer mentions 404, because Elysia keeps that status by itself. Tests untouched, both pass. A second refactor: commit.

Could the framework handle "page not found" more gracefully?

Other frameworks do. They fall into three styles.

  • A file with a special name, no code: Rails, Django, Laravel, Next.js and Phoenix look for a page named for 404.
  • A named place for exactly this: Hono has notFound, Fastify has setNotFoundHandler, Flask has errorhandler(404).
  • One general error hook where you check what went wrong: Elysia and Express.

So there is room for a small helper of our own, and perhaps a contribution to Elysia later. We decided to wait: three lines used once do not justify a helper. When a second error page arrives, the helper's shape will be clear.

The habit to take away

When you bring in a tool, ask twice. First: do I need it yet? Second, once it is in: what am I still doing by hand that it already does?

A step further

Notice the swap was made with zero edits to the test file because the tests drive the app from outside, through a browser. Tests that reach into internals would have had to be rewritten, and a rewritten test cannot vouch for a refactor.

Try it yourself

git checkout 6506af3 && bun install && bun test   # before: 2 pass
git checkout 4fcaf6c && bun install && bun test   # Elysia: 2 pass
git checkout d7022ca && bun install && bun test   # add-on: 2 pass
git diff 6506af3 d7022ca -- features/

The last command prints nothing. That empty output is the proof: across both refactors, the tests did not change by a single character.

What is the difference between a dependency and a peer dependency?

A dependency is the library's private tool, with its own copy. A peer is owned by the project and shared, so there is exactly one copy. Mark a package as a peer when its objects cross between your code and the library, or when a plug-in must attach to the one host.
