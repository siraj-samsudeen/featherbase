# Tasks — phase gates, not blanket execution permission

The owner authorized this contract revision, not candidate launch. An Opus manager starts only when the owner sends the launch prompt. Each later phase requires a new owner approval. Check boxes record evidence, not permission inferred from OpenSpec artifact completion.

## 1. Phase 1 — bare CRUD

- [ ] 1.1 Record launch authorization, exact contract commit, shared worker model/toolchain/UI baseline and equivalent orb resources; verify the manifest and all host prerequisites before dispatch.
- [ ] 1.2 Build a separate minimal Phase-1 HTTP/browser/restart harness with negative controls; verify its selftests, requirement-to-test mapping and frozen commit without changing historical `suite/`.
- [ ] 1.3 Launch the three fresh candidates for Phase 1 only, recording assignment and delivery timestamps; verify documented commands and source/lockfile archive hashes.
- [ ] 1.4 Independently run CRUD and same-data restart checks, preserve first and repaired results, inspect a desktop/mobile preview and verify a disposable restore of each retained database backup.
- [ ] 1.5 Present timings, correction causes, functional evidence and previews; stop and record owner review/approval before Phase 2.

## 2. Phase 2 — evolution and contracts

- [ ] 2.1 After approval, freeze cumulative Phase-2 tests including populated upgrades, null/value rules and contract negative controls; verify those controls detect deliberately wrong results.
- [ ] 2.2 Preserve and run the nullable-priority revision on retained data, then the backfill/NOT NULL revision; verify IDs, values, deletions, SQL constraint, fresh install, reruns and failed/concurrent migration behavior.
- [ ] 2.3 Verify derived browser contracts with an incompatible-change compile failure and actual response-path runtime negative controls; verify generated OpenAPI with an independent HTTP client and document native integration gaps.
- [ ] 2.4 Present cumulative acceptance, migration manifests, timing/correction deltas and previews; stop for owner approval before Phase 3.

## 3. Phase 3 — relationships and dependable writes

- [ ] 3.1 After approval, freeze cumulative relationship/recovery/conflict/process tests and validate fault injection; ensure missing request identities and removed-checkbox re-resolution do not repeat historical harness defects.
- [ ] 3.2 Independently verify Projects, Todo relationships, completion/filters/title rules, populated upgrades and unchanged unrelated records through API and UI.
- [ ] 3.3 Verify competing writes, deleted-record recovery, lost create replies, replacement drafts and unrelated-action recovery ownership on desktop/mobile; retain original failures and exact saved outcomes.
- [ ] 3.4 Verify truthful readiness during outage, real-listener graceful/forced shutdown, exact-instance cleanup and immediate same-build restart on disposable data; present evidence and stop for owner approval before Phase 4.

## 4. Phase 4 — UI finish

- [ ] 4.1 After approval, publish one shared visual brief/component baseline and freeze same-steps keyboard/feedback/layout checks; verify direct-input Enter and render-settled focus are actually exercised.
- [ ] 4.2 Independently exercise creation, save/cancel, deletion, validation, retry and conflict review; inspect desktop/mobile screenshots of representative states and record focus plus current feedback.
- [ ] 4.3 Record actual zoom, accessibility/contrast and screen-reader/device checks or explicit unassessed limitations; present functional results separately from owner visual inspection and stop before Phase 5.

## 5. Phase 5 — declarative Todo and named extensions

- [ ] 5.1 Present the minimal declaration format and typed named extension catalogue for owner approval; verify it covers the accepted Todo app without speculative ERP features.
- [ ] 5.2 After approval, extract generic behavior while preserving retained data; run cumulative acceptance against the declaratively defined Todo app and inspect core for Todo-specific branches/copied resource implementations.
- [ ] 5.3 Load Supplier through the same build's runtime definition mechanism; verify generated API/UI/schema behavior without core edits and preserve the source diff and data manifest.
- [ ] 5.4 Independently run named validator/renderer extension tests, including rejected-write preservation, unknown-name activation failure and keyboard/error behavior; verify documented types, ordering and transaction/failure boundaries.
- [ ] 5.5 Present the final ten-category comparison, phase-by-phase timing/corrections, native versus custom responsibilities, inspected previews and unresolved limitations; stop for owner selection without merge or deployment.
