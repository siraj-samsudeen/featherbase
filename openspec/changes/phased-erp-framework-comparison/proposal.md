# Proposal

## Why

Choose a foundation for a metadata-driven ERP application framework, not the best isolated Todo implementation. Small, owner-reviewed phases distinguish first-delivery speed, safe evolution, recovery, UI finish, and actual reuse instead of charging every complexity to the first delivery.

## What Changes

- Compare fresh AdonisJS, Encore.ts, and Elysia implementations with the same React/Vite UI stack and equivalent environments.
- Progress through five separately accepted phases: bare CRUD; safe evolution and contracts; relationships and dependable writes; UI finish; declarative extraction and named extensions.
- Stop after every phase for owner review. Build only the authorized phase; do not front-load future features or framework abstractions.
- Finish by defining the Todo application declaratively, exposing unsupported behavior through documented named extension points, and proving reuse with a third resource.
- Preserve the previous six-stack contract, frozen suite and results as historical evidence. They do not impose later-phase requirements on the new Phase 1.

## Capabilities

### New Capabilities

- `phased-comparison`: Cumulative application outcomes and acceptance boundaries for this new five-phase experiment.

### Modified Capabilities

None. The earlier `todo-release-1` change is a historical experiment, not the baseline specification for these new candidates.

## Impact

This revision is planning only. It does not implement a new harness, launch candidates, merge, deploy, or modify retained databases. The future manager must prepare phase-specific acceptance before each implementation phase. The current `suite/` is historical and must not be run wholesale against Phase 1.

The owner requested an Opus management prompt; prompts point to this contract rather than carrying hidden requirements. Existing candidate sources, failed results and retained databases remain untouched. No existing candidate is silently substituted for a fresh attempt.
